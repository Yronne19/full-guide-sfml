CMake in VS Code

CMake does not compile your code. It reads CMakeLists.txt and generates the build files for your compiler (MSVC, MinGW, GCC, Clang). VS Code’s CMake Tools extension runs it for you.

Setup

  1. Install a compiler: on Windows, “Build Tools for Visual Studio” (MSVC) or MSYS2 MinGW. On Linux, sudo apt install build-essential cmake.
  2. Install CMake from cmake.org and tick “Add to PATH”. Check with cmake --version.
  3. In VS Code install the extensions C/C++ and CMake Tools (both from Microsoft).
  4. Press Ctrl+Shift+P, run CMake: Select a Kit and pick your compiler.
  5. Build with the Build button in the bottom bar (or F7), run with the play button.
Using MSVC? Open VS Code from the “Developer Command Prompt”, or just pick the Visual Studio kit. Using MinGW? Add its bin folder to PATH.

The five SFML modules

SFML is split into modules, and each one is its own CMake target. Including <SFML/Graphics.hpp> also brings in Window and System.

  • System: time, clocks, vectors, angles.
  • Window: the window, events, keyboard and mouse.
  • Graphics: textures, sprites, shapes, text, cameras.
  • Audio: sound effects and music.
  • Network: TCP and UDP sockets, packets.

Making a UI

SFML has no ready-made buttons or text fields, so you build small classes from shapes and text. Draw the UI after calling window.setView(window.getDefaultView()) so it does not move with the camera. You need any .ttf font file, for example C:/Windows/Fonts/arial.ttf copied into your assets folder.

Tips and tricks for game logic

These habits keep an SFML game smooth and keep MySQL from freezing it. Each one has a small example you can paste in.

1. Keep update and draw separate

Change the game state first (move, collide, punch), then draw it. A fixed timestep makes physics behave the same on slow and fast PCs.

2. Never call MySQL inside the game loop

A query can take 5 to 500 ms, and the game freezes for that long. Load once at start, then save from a background thread. One MySQL connection must only be used by one thread, so create it inside the worker.

3. Save only what changed

The world array is the truth while playing. Remember which tiles changed (a “dirty” list) and write only those, in one transaction. Saving 450 tiles every frame would be far too slow.

4. Put block rules in a table, not in if-chains

5. Convert mouse pixels to world coordinates

Once you use a camera (sf::View), the mouse position in the window is not the position in the world.

9. Buying items: use a transaction

Taking gems from the player and giving the item must happen together or not at all. The gems >= 50 check inside the UPDATE stops a player from going below zero, even if two requests arrive at once.

Quick rules

  • Save on events (leaving the world, buying something), plus a timer every 30 seconds. Not every frame.
  • Load everything you need before the loop starts, and show a loading text while you do.
  • Use game states (enum class State { Login, Playing }) so the login screen and the world do not mix their code.
  • Draw only what is on screen: loop over the tiles inside the camera, not the whole map.
  • Check for errors on every DB call and keep playing offline if the database is down.
  • Test small: make one feature work (punch a block), save it, reload it, then add the next.
